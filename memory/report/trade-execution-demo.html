交易执行链路 — 谁来负责下单？

Agent 团队负责分析和建议，但真正的下单由谁执行？答案是：一个不含 LLM 的确定性系统进程。

先说结论

Agent 团队（LLM 驱动）
负责：分析市场、评估风险、生成建议
不负责：实际下单、管理订单、与交易所交互
原因：LLM 有幻觉风险，不能让它碰真钱
Executor（系统进程，无 LLM）
负责：接收确认后的订单、与交易所交互、监控状态
特点：纯代码逻辑，无 LLM，确定性执行
类比：银行柜台——你说"转5000"，它精确执行，不会"理解"错
为什么不能让 Agent（LLM）直接下单？

1. LLM 有幻觉 — 它可能"以为"价格是 $94,000，实际已经变了
2. LLM 不精确 — "买入 0.11 BTC" 可能被 LLM 处理成 "买入 0.1 BTC" 或 "买入 1.1 BTC"
3. LLM 不确定性 — 同样的 prompt 第二次跑可能生成不同参数的订单
4. 延迟 — LLM 调用需要秒级延迟，交易需要毫秒级

所以：分析用 LLM，执行用确定性代码。两者之间的桥梁是用户的确认点击。

Executor 内部结构

Executor 不是 Agent 角色，是系统进程 无 LLM
纯 Rust 代码实现，确定性执行，毫秒级响应。它和 Agent 团队完全隔离。
模块 Pre-Flight Check
下单前的硬编码检查：余额充足、仓位合规、API 连通、无重复订单、未触发熔断。全部通过才放行。
模块 Order Submitter
向交易所 API 提交订单。支持市价单、限价单。大额订单可拆分执行（TWAP/冰山单）。
模块 Status Monitor
轮询订单状态直到终态（成交/取消/过期）。超时（如 60 秒限价单未成交）自动处理。
模块 Post-Execution
成交后：更新本地持仓、记录到 Track Record、通知 Sentinel 监控、生成滑点报告。
模块 Circuit Breaker
熔断器：连续失败 N 次、单日亏损超阈值、API 异常 → 自动冻结下单能力，通知用户。
模块 Audit Logger
完整审计日志：每笔订单的确认时间、提交时间、成交时间、价格、滑点、发起来源。不可篡改。

异常场景怎么处理

Executor 的容灾机制
⚠️
场景 1：下单后 API 断连
订单已提交到交易所，但网络断了，拿不到成交结果。
处理： 1. 标记订单为 "UNCERTAIN" 状态 2. 30 秒后重试查询订单状态 3. 如果仍无法连通 → 冻结后续下单 4. 通知用户："订单 ORD-8847 状态未知，请手动在交易所确认" 5. 网络恢复后自动同步真实订单状态 绝不在状态未知时提交新订单。
⚠️
场景 2：限价单长时间未成交
限价买入 0.11 BTC @ $94,320，但价格涨到了 $95,000，一直挂着。
处理： 1. 超时 60 秒后通知用户： "限价单未成交，当前价格 $95,000（+0.72%）" 2. 提供选项： A) 继续挂单等待 B) 改为市价单立即成交 C) 取消订单 3. 用户无响应 → 默认保持挂单（不主动取消）
⚠️
场景 3：Pre-Flight 余额不足
用户确认下单时余额充足，但提交到交易所时已被其他挂单占用。
处理： 1. Pre-Flight 检查时锁定可用余额（扣减挂单占用） 2. 如果仍然不足 → 拒绝下单 3. 通知用户："可用余额不足（$X 被挂单占用），请取消部分挂单后重试" 4. 绝不降低数量自动下单 — 数量由用户确认，Executor 不改
⚠️
场景 4：单日熔断触发
当日已亏损超过用户预设的最大回撤（如总资金 5%）。
处理： 1. Circuit Breaker 触发 → 冻结所有新订单提交 2. 通知用户 + Sentinel： "⚠ 单日亏损已达 5%，下单功能已冻结" 3. 用户可手动解除冻结（需输入确认码） 4. 冻结期间 Agent 团队仍可正常分析，只是不能执行 冻结是保护机制，不是惩罚。

Executor 在整体架构中的位置

─── Agent 世界（LLM 驱动） ────────────────────── 用户: "按分析买入 BTC" │ ├─ Planner → 调度 Risk ├─ Risk → 计算仓位: 0.11 BTC ├─ Coordinator → 生成确认卡片 │ └─ → 用户确认 ← 分水岭：LLM 世界到此为止 │ ─── 系统世界（纯代码，无 LLM） ───────────────── │ ├─ Executor │ ├─ Pre-Flight Check（硬编码规则） │ ├─ Order Submitter（交易所 API） │ ├─ Status Monitor（轮询状态） │ ├─ Post-Execution（更新持仓） │ ├─ Circuit Breaker（熔断保护） │ └─ Audit Logger（审计日志） │ └─ → 执行结果返回 Agent 世界 └─ Coordinator 生成成交报告
总结：交易执行的三个关键设计

1. Agent 和 Executor 完全隔离 — Agent 产出建议（JSON），Executor 接收确认后的订单参数。两者之间没有 LLM 调用。

2. 用户确认是分水岭 — 确认之前是 LLM 世界（可能有幻觉、不确定性），确认之后是代码世界（确定性、毫秒级、可审计）。

3. Executor 只做用户确认的事 — 它不会修改数量、不会改价格、不会"智能优化"。用户确认什么，它精确执行什么。如果执行不了（余额不足/API 断连），它拒绝并通知用户，而不是擅自调整。
