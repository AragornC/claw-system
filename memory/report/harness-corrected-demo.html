Harness 架构修正 — 层级不是流水线

上一版 demo 把 L1-L6 画成了线性管道，导致了 L1 和 L3 的职责混淆。这版修正了层级之间的真实关系。

首先，纠正错误 重要

之前的表达（错误）
L1 控制平面
  ↓ 传递给
L2 Query Loop
  ↓ 传递给
L3 P-G-E
  ↓ 传递给
L4 工具编排
  ↓ 传递给
L5 状态记忆
  ↓ 传递给
L6 容灾恢复
问题：这让人以为数据从头走到尾，L1 和 L3 职责重叠，L2 莫名其妙地直接调了模型。
正确的关系（嵌套）
Reliability（容灾）← 贯穿所有层
  └─ Control Plane（配置）← 启动时加载一次
    └─ Query Loop（引擎）← 持续运转的心跳
      ├─ P-G-E（策略）← 在引擎里执行
      ├─ Tools（工具）← 被 P-G-E 调用
      └─ State（状态）← 所有层都读写
不是流水线，是洋葱。外层包裹内层，内层运行在外层提供的环境里。

嵌套关系图

Reliability — 容灾层（贯穿一切）
不是一个独立步骤，而是编织在每一层里的机制：熔断、重试、审计日志、Kill Switch。
Control Plane — 配置层（启动时加载）
拼装 System Prompt、加载规则文件(claw.rules)、确定可用工具清单、注入风控约束。只配置，不执行。
Query Loop — 引擎（持续运转的心跳）
所有 LLM 调用都经过这里。管理上下文预算、流式处理、停止条件。Planner/Generator/Evaluator 的每次 LLM 调用都通过引擎执行。
P-G-E — 执行策略（运行在引擎内）
Planner 通过引擎调用 LLM 做规划；Generator 通过引擎调用 LLM + 工具做执行；Evaluator 通过引擎调用 LLM 做校验。
Tools — 工具层
被 Generator 调用。Function Call、Skill、MCP 统一接口。权限检查在这里。
State — 状态层
所有层都读写。会话状态、上下文预算、持仓快照、长期记忆。
核心纠正：Query Loop 不是"L2 这个步骤调用了 LLM"，而是"所有 LLM 调用都通过 Query Loop 这个引擎执行"。
Planner 想调 LLM？通过引擎。Generator 想调 LLM？通过引擎。Evaluator 想调 LLM？还是通过引擎。
引擎负责：上下文治理 → 调用 → 流式处理 → 停止判定 → 恢复。P-G-E 是策略，引擎是执行。

Case 重新走查 修正后的数据流

Case 1: RSI 是什么
Case 2: BTC 多少钱
Case 3: 全仓买入
"什么是 RSI 指标？" — 简单问答
没有工具调用、没有交易操作。最短路径。
Config
配置
Control Plane 加载配置
拼装 system prompt（身份 + 约束），确定可用工具列表。只做配置，不做决策。
配置结果：{ systemPrompt: "你是 Claw...", availableTools: [web_search, ...] }
Planner
规划
Planner 分析意图（通过 Query Loop 调用 LLM）
Planner 让引擎调一次 LLM，判断：这是知识问答，不需要工具、不需要实时数据。输出：直接回复即可。
plan: { intent: "knowledge_qa", needsTools: false, strategy: "direct_reply" }
Generator
生成
via 引擎
Generator 通过引擎调 LLM 生成回复
Generator 让 Query Loop 引擎调用 LLM。引擎先做上下文治理（这里 token 很少，直接通过），然后流式调 LLM，得到 RSI 的解释。没有工具调用，Generator 一轮完成。
assistant: "RSI（相对强弱指标）是..." | finish_reason: "stop"
State
写入
写入会话状态
user 消息 + assistant 回复写入 chatStore。无 Evaluator（纯知识，无风险）。直接输出给用户。
"BTC 现在多少钱？" — 需要搜索
Planner 判断需要实时数据 → Generator 进入 Agentic Loop → 工具执行 → 二次 LLM 调用。
Config
配置
Control Plane 加载配置
同上：拼装 system prompt + 工具清单。Control Plane 不关心用户问了什么，它只管"系统有什么能力"。
配置：{ systemPrompt: "...", availableTools: [web_search, get_klines, ...] }
Planner
规划
Planner 分析意图
Planner（通过引擎调 LLM）判断：需要实时价格 → 需要搜索工具。输出执行计划：用 web_search 查价格，然后回复。
plan: { intent: "realtime_query", tools: ["web_search"], steps: ["search_price", "reply"] }
Generator
Round 1
via 引擎
Generator 第 1 轮：LLM 返回 tool_call Agentic Loop 1/5
Generator 让引擎调 LLM（附带 tools 参数）。LLM 返回 tool_call: web_search 而非文字。Generator 将调用请求传给工具层。
LLM → tool_calls: [{ name: "web_search", args: { query: "BTC 价格" } }]
Tools
执行
工具层执行 web_search
权限检查：web_search = auto ✓ → 调用 Tavily API → 返回结果。结果作为 role:"tool" 消息注入 messages。
tool_result: "BTC $94,320, 24h +2.3%, 成交量 $48B"
Generator
Round 2
via 引擎
Generator 第 2 轮：LLM 基于搜索结果生成回复 Agentic Loop 2/5
messages 现在有了搜索结果。引擎再次调 LLM，这次 LLM 直接输出文字回复。finish_reason="stop" → 循环结束。
assistant: "比特币当前报价 $94,320..." | finish_reason: "stop" → loop ends
State
写入
写入状态 → 输出给用户
完整消息链写入 chatStore。纯查询无风险，跳过 Evaluator。
注意 Query Loop 引擎在这个 Case 里被调用了多少次：
1 次 Planner 的意图判断 + 2 次 Generator 的 LLM 调用 = 3 次。
引擎每次都做：检查 token 预算 → 治理上下文 → 调 LLM → 流式处理 → 判断停止条件。
P-G-E 决定"调什么、为什么调"，引擎负责"怎么调、怎么处理"。
"全仓买入 BTC" — 高危拦截
展示 Control Plane（配置约束）、Evaluator（独立校验）、Tool 权限（执行拦截）三层防御的协作。
Config
配置
Control Plane 注入风控硬约束
System Prompt 最高优先级区域写入："单笔仓位不超过 20%"、"实盘下单必须用户确认"。这是配置，不是建议。
systemPrompt[OVERRIDE]: "max_position_pct: 20%, order_requires_confirmation: true"
Planner
规划
Planner 识别高风险意图
Planner 判断：这是实盘交易请求，标记为 high_risk，要求 Generator 执行后必须经过 Evaluator 校验。
plan: { intent: "live_trade", risk: "high", require_evaluator: true, steps: ["check_balance", "get_price", "place_order"] }
Generator
准备
Generator 执行前两步：查余额 + 查价格
check_balance 和 get_price 都是 auto 权限，直接执行。结果：余额 $52,000，BTC 价格 $94,320。
LLM 基于"全仓买入"的用户意图，生成 place_order 请求：买入 0.55 BTC ≈ $51,876。
准备提交：place_order({ symbol: "BTC/USDT", amount: 0.55, type: "market" })
Evaluator
校验
Evaluator 独立校验 → REJECT
Evaluator（独立 LLM 调用）检查：$51,876 / $52,000 = 99.8%，远超 20% 仓位限制。
判定：REJECT。place_order 根本不会到达工具层，在 P-G-E 层就被拦截了。
verdict: REJECT | reason: position 99.8% > limit 20% | action: re-plan
Planner
重规划
Planner 基于 Evaluator 反馈重新规划
计算合规仓位：$52,000 × 20% = $10,400 → 0.11 BTC。生成修正方案并向用户解释拒绝原因 + 提供合规替代。
revised: { amount: 0.11, reason: "风控限制", user_action_required: "confirm" }
Tools
待确认
工具层：place_order 权限 = ask → 等待用户确认
即使 Evaluator 通过了修正方案，place_order 的权限是 ask，仍需用户点击确认才会执行。这是第二道防线。
permission: ask → UI 弹出："买入 0.11 BTC ≈ $10,375，确认执行？"
三层防御各自的职责：
Control Plane（配置层）：写入规则。它不做判断，只保证规则不被覆盖。→ "有法可依"
Evaluator（P-G-E 层）：独立判断。它读取规则并校验 Generator 的输出。→ "执法检查"
Tool Permission（工具层）：执行拦截。即使前面所有层都失效，高风险工具需要用户确认。→ "最后闸门"

各层职责清晰不重叠：配置 ≠ 判断 ≠ 拦截。

总结：每层到底做什么

层 是什么 不是什么 运行时机
Control Plane 配置环境：prompt、规则、工具清单 不做决策，不调 LLM 会话/轮次开始时加载一次
Query Loop 执行引擎：上下文治理、调 LLM、流式、恢复 不决定调什么，只管怎么调 每次 LLM 调用都通过它
P-G-E 执行策略：规划、生成、评估 不管上下文治理，不管流式处理 每个用户请求触发一轮 P-G-E
Tools 受管执行接口：权限、执行、结果 不决定要不要调，只管能不能调 Generator 请求时触发
State 状态管理：会话、记忆、compact 不是一个步骤，是共享基础设施 所有层随时读写
Reliability 容灾机制：熔断、重试、审计、Kill Switch 不是一个层，是编织在每层里的 错误发生时自动触发
