Skill vs Tool — 为什么需要 Skill 抽象？

同一个任务"设计一个成交量异常因子"，分别用纯工具和 Skill 两种方式完成，对比效果差异。

同一个需求，两种方式

方案 A：只用工具，没有 Skill
用户
帮我设计一个基于成交量异常的交易因子
Planner（LLM 自己判断）
LLM 需要从零理解"因子设计"的完整流程。
它必须自己决定：查什么资料、用什么指标、怎么回测、评估标准是什么。

这些全靠 LLM 的训练知识，没有任何领域约束。
Generator 执行
web_search("volume anomaly trading")
code_exec(写因子代码)
get_klines(取数据)
code_exec(跑回测)

但是...
用了未来数据（前视偏差） 没验证因子稳定性 回测没扣手续费 没考虑换手率 没做多品种验证 每次结果不一致
Evaluator
Evaluator 也不知道"好因子"的标准是什么。
它只能用通用逻辑去猜，大概率放过了上面的问题。
方案 B：使用 factor_design Skill
用户（完全一样的输入）
帮我设计一个基于成交量异常的交易因子
Planner（匹配到 Skill）
Skill 匹配：factor_design
注入领域知识：因子设计标准流程、评估指标定义、质量红线。
Planner 不需要"猜"怎么做，Skill 已经定义了标准工作流。
Generator 按 Skill 工作流执行
Step 1 研究：web_search → 学术方案
Step 2 设计：代码生成 + Skill 约束：禁止使用未来数据
Step 3 回测：Skill 要求：必须扣手续费 0.1% + 滑点 0.05%
Step 4 评估：Skill 定义：IC>0.03, IR>0.5, 换手率<30%
Step 5 验证：Skill 要求：至少 2 个品种交叉验证
标准化流程保证 领域质量红线 每次执行一致 Evaluator 有明确标准
Evaluator（有 Skill 提供的评估标准）
按 factor_design Skill 的质量标准逐项检查：
IC=0.08 ✓ | IR=1.2 ✓ | 换手率 22% ✓ | 无前视偏差 ✓ | 多品种 ✓
核心区别：Skill 封装了领域专家的知识，把"做对的标准"变成了可执行的约束。
没有 Skill 时，LLM 每次都在"即兴发挥"，结果不可控。有了 Skill，LLM 是在"按规范执行"，结果可重复、可验证。

类比：工具是"锤子、锯子、螺丝刀"，Skill 是"一份带着质检标准的施工图纸"。你不能只给工人工具就让他盖楼，还得给图纸。

注入给 LLM 的领域约束（Prompt 片段）
你正在执行「因子设计」任务，必须遵守以下规范： 1. 严禁使用未来数据（前视偏差），所有计算必须用 shift(1) 滞后 2. 回测必须扣除手续费（默认 0.1%）和滑点（默认 0.05%） 3. 因子评估必须包含：IC、IR、换手率、最大回撤 4. 最终因子必须在至少 2 个品种上交叉验证 5. 如果 IC < 0.03 或 IR < 0.5，标记为不合格
Evaluator 评估标准
评估维度： - IC > 0.03 (信息系数，因子预测力) - IR > 0.5 (信息比率，风险调整后收益) - 换手率 < 30% (过高换手会吃掉手续费) - 无前视偏差 (代码审查) - 多品种一致性 (至少 2 个品种 IC 同向)

Tool vs Skill vs P-G-E — 三者关系

概念 是什么 包含什么 类比
Tool 原子操作 一个函数：输入 → 执行 → 输出。无领域知识，无流程概念。 锤子、锯子
Skill 领域能力包 工具组合 + 标准工作流 + 领域约束（Prompt 片段）+ 质量标准（Evaluator 标准） 施工图纸 + 质检规范
P-G-E 执行引擎 Planner 匹配 Skill → Generator 按 Skill 工作流执行 → Evaluator 按 Skill 标准验证 项目经理 + 施工队 + 质检员
它们之间的调用关系
用户: "帮我设计一个成交量异常因子" │ ┌───────▼───────┐ │ Planner │ "这个需求匹配 factor_design Skill" │ │ → 加载 Skill 的工作流 + 约束 + 评估标准 └───────┬───────┘ │ ┌───────▼───────┐ │ Generator │ 按 Skill 定义的工作流逐步执行 │ │ 每步调用 Tool（web_search / code_exec / backtest） │ │ Skill 的约束注入 Prompt → LLM 遵守领域规范 └───────┬───────┘ │ ┌───────▼───────┐ │ Evaluator │ 按 Skill 定义的质量标准逐项检查 │ │ IC > 0.03? IR > 0.5? 无前视偏差? │ │ PASS → 输出 | REVISE → 回 Generator └───────────────┘
回到你的问题：因子生成应该是 Tool 还是 Skill？

答案：一定是 Skill。因为因子设计不是一个原子操作，它是一个有标准流程、有质量要求、需要多个工具协作的领域能力。

Tool 解决的是"能不能做"（有没有搜索、有没有回测引擎）。
Skill 解决的是"做得对不对"（流程对不对、质量达不达标、有没有犯常见错误）。

Skill 的本质是把领域专家的经验编码成了可执行的约束。没有 Skill，你的 Agent 就是一个什么都懂一点但什么都不精的通才；有了 Skill，它在特定领域就是一个按规范执行的专业人员。
