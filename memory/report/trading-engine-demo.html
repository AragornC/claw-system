Agent → 交易引擎 — 策略的生命周期

Agent 团队是大脑，交易引擎是身体。大脑想出策略，交给身体持续运行。
但身体不能脱离大脑的监督——而最终的控制权在用户手里。

先区分两种模式

手动交易（上一个 demo 讲的）
触发：用户在对话框说"买 BTC"
流程：Agent 分析 → 确认卡片 → 用户确认 → Executor 执行一笔
结束：这一笔成交后就完了
类比：手动开车——你踩油门，车走一步
策略交易（这个 demo 要讲的）
触发：用户说"帮我部署一个均线交叉策略"
流程：Agent 设计策略 → 回测 → 用户审批 → 部署到交易引擎 → 持续运行
结束：策略一直跑着，条件触发就下单，直到用户暂停/停止
类比：自动驾驶——你设定目的地，车自己开，但你随时可以接管
策略交易才需要交易引擎。手动交易用 Executor 就够了。
交易引擎 = 一个持续运行的策略运行时，它根据策略定义的条件自动监控市场、生成信号、触发下单。

一个策略从诞生到运行的完整生命周期

用户: "帮我做一个 BTC 均线交叉策略，回测通过就部署"
🧠
PHASE 1 — Agent 世界
策略设计与验证
Planner 调度 Quant + Risk：
Quant（strategy_backtest Skill）→ 设计策略、编写代码、回测验证
Risk（position_sizing Skill）→ 计算合理仓位、设定风控参数
Coordinator → 综合策略报告 + 回测结果
strategy_definition: { name: "MA_Cross_BTC", type: "trend_following", symbol: "BTC/USDT", timeframe: "4h", // 策略逻辑（确定性规则，不含 LLM） entry: { condition: "MA(20) crosses above MA(60)", side: "buy", size: "balance * 0.10" // 10% 仓位 }, exit: { take_profit: "+5%", stop_loss: "-3%", trailing_stop: "-2% from peak", condition: "MA(20) crosses below MA(60)" }, // 风控参数（Risk Agent 设定） risk: { max_position_pct: 10, max_daily_loss: 500, // $500/天 max_concurrent_orders: 1, cooldown_after_loss: "4h" // 止损后冷静 4 小时 }, // 回测结果 backtest: { period: "2025-10 ~ 2026-03", sharpe: 1.82, max_drawdown: "8.2%", win_rate: "58%", total_return: "+23.5%" } }
👤
PHASE 2 — 用户审批
审核策略 + 选择运行模式
用户审阅策略定义、回测结果、风控参数。然后选择运行模式：
📝
模拟盘
不涉及真钱。策略在真实市场数据上运行，但订单只是"纸上交易"。
适用：首次部署、验证策略有效性
风险：零
下单审批：不需要
🔔
信号通知
策略运行并生成信号，但不自动下单。每次信号推送给用户，由用户决定是否执行。
适用：有一定信心但不想全自动
风险：零（不自动下单）
下单审批：每次都要
⚡
自动执行
策略信号触发后自动通过 Executor 下单。在预设的风控范围内自动运行。
适用：充分验证后的成熟策略
风险：有（真金白银）
下单审批：预授权（在风控范围内免确认）
三种模式是渐进式信任：模拟盘 → 信号通知 → 自动执行。
用户可以先在模拟盘跑 2 周，满意了切到信号通知跟几天，最后才开自动执行。
任何模式都可以随时暂停。自动执行模式下，风控参数（最大仓位、止损、日亏上限）是硬锁的。

交易引擎内部结构

Trading Engine 系统进程，无 LLM
交易引擎和 Executor 一样是纯代码进程，不含 LLM。它运行的是用户审批过的确定性规则，不做任何"推理"。
核心 Strategy Runtime
加载策略定义，按 timeframe 轮询市场数据，计算指标，判断进出场条件。纯规则引擎，无 LLM。
核心 Signal Generator
当策略条件满足时生成交易信号。信号包含：方向、品种、数量、价格、信号强度。
调度 Order Router
根据运行模式路由信号：模拟盘→记录不执行 | 信号通知→推送用户 | 自动执行→发给 Executor。
调度 Position Manager
跟踪策略的持仓状态。管理止盈止损单。计算浮动盈亏。一个策略一个独立的持仓簿。
风控 Risk Guard
实时检查策略是否越界：仓位超限？日亏过大？信号频率异常？触发则冻结该策略。
监控 Performance Tracker
记录策略的实盘表现：每笔交易、累计收益、Sharpe、回撤。供 Agent 团队复盘和用户查看。

Risk Guard 检查
信号过风控
即使是自动执行，每个信号仍需通过硬编码风控检查：

建仓后继续监控：止损单是否触发、是否达到止盈、是否出现死叉退出信号。

Agent 团队和交易引擎的关系

三者各司其职
━━━ Agent 团队（LLM 驱动）━━━━━━━━━━━━━━━━━━━ 职责：策略设计 + 回测验证 + 风控参数 + 持续优化建议 产出：strategy_definition（JSON，确定性规则） 什么时候介入： → 初始设计策略 → Sentinel 发现策略表现衰减时，提出优化建议 → 用户要求修改策略时 → 定期复盘时 ━━━ 用户（决策者）━━━━━━━━━━━━━━━━━━━━━━━━━ 职责：审批策略 + 选择运行模式 + 随时暂停/修改 什么时候介入： → 审批新策略上线 → 审批策略参数修改 → 信号通知模式下确认每笔订单 → 主动暂停/停止策略 ━━━ 交易引擎 + Executor（系统进程，无 LLM）━━━━ 职责：运行策略 + 执行订单 + 风控护栏 + 记录表现 什么时候运行： → 7×24 持续运行（策略激活期间） → 按 timeframe 轮询（如每 4h / 1h / 15m） → 信号触发时立即响应
交易引擎运行的是"确定性规则"，不是 LLM 推理。

Agent 团队产出的 strategy_definition 是一份结构化的 JSON——条件、阈值、参数全部是硬编码的数字和规则。
交易引擎拿到这份 JSON 后，就像一个规则引擎一样运行它：if MA20 > MA60 then BUY。
运行时不需要 LLM，不需要"理解"，不需要"推理"。

LLM 的价值在前面——帮你设计这套规则。而不是在运行时做每一个交易决策。

完整系统架构

三个系统各自的边界非常清晰：

Agent 团队 — 产出策略定义（JSON），提出优化建议，做复盘分析。不碰执行。
交易引擎 — 运行策略规则，生成信号，管理持仓。不做推理。
Executor — 与交易所交互，提交订单，监控状态。不做决策。

LLM 只存在于 Agent 团队里。交易引擎和 Executor 是纯代码，确定性执行。
这样即使 LLM 出问题（幻觉、宕机），正在运行的策略不受影响——因为策略已经被编译成确定性规则了。
